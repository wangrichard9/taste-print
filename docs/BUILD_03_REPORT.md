## What changed for Tasteprint

Discover now asks the saved raw co-like model to rank unseen recipes from explicit likes. Each supported result shows actual fitting-data shared-liker evidence with one of the person's liked recipes. This is not a probability, a learned ingredient ban, or a claim to understand nuanced taste. Passes exclude that recipe only; saves remain a separate collection. Empty/all-pass profiles and recipes without shared-like evidence use explicitly labeled fitting popularity. Loading and service failure are visible; failure leaves catalog browsing working without pretending it is personalized.

The catalog now contains **5,006 unique model recipes**, rather than only the 30 original display recipes. The 30 retain every original field and identity, and all are supported by the model. The other 4,976 are bulk-exported source metadata; no manual-review claim, ingredient/quantity pairing, invented nutritional claim or dietary-safety guarantee is added. A source category is the only tag for bulk records. Fresh/Comfort editorial filters therefore remain scoped to the reviewed collection, explicitly explained in Discover. Source metadata contains 4,946 allowed-host photo links and 60 missing-photo records; live availability/correspondence of every new photo was not verified.

Original source directions for bulk recipes load only when opening a detail view; they are not bundled for every card. Reported times/servings, ingredients and original recipe/dataset links are preserved. Missing directions/service error refer the person to the original source and allow retry. React renders source strings as text, not HTML. Existing six starters are all model-supported; finishing onboarding now opens live Discover. Closing onboarding still discards draft edits. Recipe summaries and source links for all candidates are in the frontend; raw reviews, people, embeddings and model matrices are not.

Discover starts with 24 cards and adds 24 on request; search applies across all candidates while preserving server ranking. Recorded choices are excluded from recommendations but accessible in Your Tasteprint or Saved. The old storage namespace and all original IDs are preserved. New recipe choices use the same existing profile schema. Ingredients, MealMerge, sample profile/inspiration and landing product scenes remain labeled design illustrations. Landing copy no longer claims only 30 recipes or no model.

## Model boundaries and data coverage

Reuse the frozen ML 04 raw relationship matrix—no refitting, extra experiment or final-test scoring. Co-like scores are the same mean over unique liked recipe relationships. Positive scores rank by descending score/ascending source ID, matching the experiment. Zero-evidence recipes are appended in popularity order and labeled separately; that serving tail is an explicit fallback policy, not a newly evaluated model improvement.

Profiles with fewer/more than six likes are mechanically supported; this does not extend the six-like quality evaluation to every profile size. No weak-link threshold or exploration quota was tuned or introduced. Returning obscure recipes is not claimed as proven taste discovery. All source recipes remain downloaded locally (522,517), but the model still uses the fixed 5,006 candidates and fitting-user interactions. Broader coverage requires a separate model/data scope. Recipe count is not training-row count: ML 04 used 305,920 positive pairs from 86,845 fitting people. Only aggregate fitting counts and recipe-to-recipe relationships are used at serving time, not validation/test histories.

## Local serving and reproducibility

`scripts/export_discover.py` validates original recipe/catalog hashes, preserves reviewed metadata and writes `src/data/model-recipes.json` plus ignored `data/processed/discover/recipes.json` and a hash manifest. `scripts/discover_service.py` verifies frozen matrix/catalog/code receipts and serving export hashes at startup. It never trains, reads final-test profiles, exposes raw-file routes or stores requests. Invalid/unknown/conflicting choices fail explicitly. JSON-only bounded request bodies, Host/Origin allowlists, no-store responses and loopback binding keep it a local demo service—not a production security claim.

`npm run dev:all` starts model and Vite together with hidden Windows child processes. Alternatively run `npm run dev:model` and `npm run dev` in separate terminals. Vite's dev/preview servers proxy `/api` to `127.0.0.1:8000`. No dependency was added. Existing local model artifacts and the project Python environment are required; npm alone on a fresh checkout is insufficient. See README for commands. Both services were started in this session for the user's existing app URL.
