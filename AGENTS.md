# Project guidance

Tasteprint is the working name of an IgniteAI Expo Data Science project.

## Context

- Before planning features, architecture, data work, or ML experiments, read `docs/PROJECT_BRIEF.md`.
- Before starting a build milestone or ML experiment, read `docs/BUILD_PLAN.md` for scope, completion criteria, and user handoffs.
- Before creating or changing UI, styling, copy, imagery, or animation, read `docs/design/DESIGN_STANDARDS.md` and `docs/design/DECISIONS.md`.
- When a design choice is resolved in conversation, record its status and rationale in `docs/design/DECISIONS.md`, then update the authoritative rule in `docs/design/DESIGN_STANDARDS.md`.

## Decisions

Explicit user decisions govern the project. Distinguish confirmed requirements, proposals, and unresolved choices in documentation. Use open design choices to generate alternatives for review; implement confirmed choices when implementation is requested.

## Collaboration

Follow `docs/COLLABORATION.md` when proposing changes, beginning implementation, or handing off completed work. Explain completed changes in Tasteprint terms, discuss the next scope with the user, and implement once the user clearly approves that scope. A roadmap entry is a proposal, not approval. Choose ordinary implementation details within agreed scope; bring material changes back for discussion.

Keep this file a concise index. Put product details in the brief and design rules in the design standards.
